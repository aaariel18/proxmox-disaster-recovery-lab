PROXMOX / RECOVERY

Backup selesai. Sistem belum tentu siap pulih.

Status backup OK baru satu bagian dari pekerjaan. Pertanyaan berikutnya: apakah VM, aplikasi, dan data benar-benar bisa dipulihkan saat dibutuhkan?

Mulai dari kemampuan memulihkan layanan

Dokumentasi ini berangkat dari Proxmox Backup & Disaster Recovery Lab di GitHub saya. Fokusnya bukan hanya membuat salinan VM, melainkan menyusun langkah pemulihan yang dapat diperiksa: backup, verifikasi, diagnosis, restore terisolasi, dan validasi layanan.

Status dokumentasi

Ini adalah technical lab dan portofolio, bukan laporan infrastruktur production perusahaan. Angka RPO/RTO aktual belum diklaim; hasil baru dicatat setelah pengujian benar-benar dijalankan.

Arsitektur: pisahkan compute dan backup

Proxmox VE menjalankan VM, sedangkan Proxmox Backup Server menjadi tujuan backup. Pemisahan host utama dan infrastruktur backup membantu mengurangi ketergantungan pada satu perangkat. Backup off-site dapat dipertimbangkan sesuai kebutuhan.

Proxmox VE / VM penting
        |
        v
Proxmox Backup Server
        |
        +-- Verification + retention
        +-- Off-site sync (opsional)
        |
        v
Restore terisolasi > validasi > cutover

Hubungkan PBS dan periksa storage

Di Proxmox VE, buka Datacenter > Storage > Add > Proxmox Backup Server. Siapkan alamat server, identitas pengguna atau token, datastore, dan TLS fingerprint yang telah diverifikasi.

pvesm status
pvesm status --storage pbs-dr

Nama pbs-dr adalah contoh ID storage. Jika storage tidak aktif, periksa koneksi jaringan, DNS, kredensial, fingerprint, firewall, datastore, dan kapasitas penyimpanan. Jangan langsung menganggap backup rusak.

Jadwal backup mengikuti kebutuhan data

Konfigurasi job melalui Datacenter > Backup > Add. Pilih VM penting, tujuan backup, jadwal, mode, dan retention sesuai kebijakan. Jadwalkan verification di PBS dan lakukan restore test, karena verification bukan pengganti pengujian aplikasi.

RPO menjelaskan toleransi kehilangan perubahan data. RTO menjelaskan target waktu pemulihan layanan. Keduanya adalah target bisnis; angka aktual harus diukur, bukan diisi supaya laporan terlihat lengkap.

Troubleshooting sebelum memutuskan restore

Aplikasi yang tidak dapat diakses belum tentu membutuhkan restore. Periksa masalah secara berlapis: aplikasi, guest OS, VM, storage, lalu host. Catat perubahan terakhir dan pertahankan log yang relevan.

# Linux guest: pemeriksaan awal
systemctl --failed
journalctl -p err -b
ip addr
ip route
df -h

# Proxmox host: ganti VMID sesuai VM tujuan
qm status <VMID>
qm config <VMID>

Untuk Windows, pemeriksaan awal dapat menggunakan Get-Service, Get-WinEvent -LogName System -MaxEvents 50, ipconfig /all, dan route print. Perintah di atas merupakan pemeriksaan; prosedur perubahan tetap mengikuti change management.

Restore ke VM lain, bukan menimpa sumber

Jika ada dugaan compromise atau corruption, isolasi sistem dan simpan bukti yang relevan. Pilih known-good restore point berdasarkan waktu kejadian dan status backup, bukan otomatis mengambil backup terbaru.

Gunakan VM ID berbeda, misalnya VM 101 untuk sumber dan VM 901 untuk recovery test. Contoh ID ini bukan kondisi sistem yang sudah diuji. Jaga VM recovery tetap terisolasi untuk menghindari benturan IP, hostname, atau identitas aplikasi.

  1. Pastikan VM boot dan filesystem dapat diakses.
  2. Periksa konfigurasi jaringan dan hindari duplicate IP.
  3. Validasi service, authentication, aplikasi, database, dan data penting.
  4. Lakukan functional test sebelum menghubungkan layanan kembali ke production.
  5. Catat waktu setiap tahap dan pantau log setelah cutover.

Ketika host Proxmox yang gagal

Siapkan recovery host, pasang Proxmox VE, lalu pulihkan konfigurasi management network, bridge/VLAN, dan storage yang diperlukan. Hubungkan kembali PBS dan prioritaskan VM layanan kritis. Boot berhasil belum berarti recovery selesai: aplikasi dan data tetap harus diperiksa.
