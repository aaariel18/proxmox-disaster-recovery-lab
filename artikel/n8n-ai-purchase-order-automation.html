N8N / AI WORKFLOW

AI membaca PO. Validasi tetap memegang kendali.

Mengubah dokumen Purchase Order menjadi JSON bukan tujuan akhirnya. Data perlu diperiksa, keputusan perlu diawasi, dan setiap langkah perlu dapat ditelusuri.

Masalahnya bukan sekadar membaca dokumen

Purchase Order dapat datang sebagai PDF atau pesan semi-terstruktur. Input ulang berulang kali membuka peluang kesalahan nama supplier, kuantitas, harga, total, dan routing persetujuan.

Repositori n8n AI PO Automation merangkum konsep alur modular: dokumen masuk, ekstraksi dengan LLM, validasi deterministik, pemeriksaan risiko, approval, penyimpanan, lalu audit log.

Ruang lingkup proyek

Ini adalah konsep otomasi enterprise untuk portofolio. Repositori menyediakan template workflow dan contoh data, bukan bukti bahwa integrasi production sudah berjalan. Kredensial dan data perusahaan tidak disertakan.

AI sebagai komponen, bukan pengambil semua keputusan

PO / webhook
      |
      v
     n8n
      |
LLM extraction -> structured JSON
      |
Validation + risk checks
      |
      +-- PostgreSQL (integrasi lanjutan)
      +-- Human approval
      |
   Audit log

Komponen dipisahkan agar provider model, database, kanal notifikasi, atau antarmuka approval bisa diganti tanpa merancang ulang seluruh proses. Keluaran LLM harus diperiksa sebelum dipakai oleh langkah berikutnya.

Apa yang disiapkan di repositori?

Materi mencakup template n8n yang dapat diimpor, prompt ekstraksi dengan kontrak output, model data PostgreSQL untuk PO dan item, contoh input/output, serta dokumentasi arsitektur.

workflows/po-ai-automation.json
prompts/po-extraction.md
database/schema.sql
examples/sample-po.json
examples/sample-output.json

Jalankan demonstrasi secara terkontrol

  1. Siapkan instance n8n untuk pengujian.
  2. Impor template workflow dari repositori.
  3. Konfigurasikan integrasi LLM dan prompt ekstraksi.
  4. Tambahkan koneksi PostgreSQL jika memperluas alur dengan node database.
  5. Kirim contoh payload ke webhook pengujian.
  6. Periksa hasil validasi, risk flag, dan keputusan approval.

Jangan memakai dokumen rahasia untuk pengujian sebelum kebijakan pemrosesan data, penyimpanan, dan provider model disetujui. Simpan API key melalui mekanisme credential atau secret management, bukan di Git.

Validasi sebelum menulis ke database

Tetapkan JSON schema yang jelas. Periksa tipe data, field wajib, hubungan item dan total, serta aturan bisnis. Gunakan ambang approval yang disepakati dan human review untuk dokumen bernilai tinggi atau hasil yang meragukan.

{
  "po_number": "PO-DEMO-001",
  "requires_approval": true,
  "risk_flags": ["REVIEW_REQUIRED"]
}

Potongan JSON tersebut hanya ilustrasi struktur, bukan hasil eksekusi workflow. Contoh lengkap tersedia di repositori sumber.

Hardening sebelum production

  • Autentikasi webhook dan validasi signature bila didukung.
  • Idempotency berbasis identitas PO, supplier, dan hash dokumen untuk mengurangi duplikasi.
  • Hak akses database minimum dan rotasi credential.
  • Penyimpanan dokumen mentah yang terkendali serta kebijakan retensi.
  • Pencatatan versi prompt, model, workflow, dan audit event.
  • Pemisahan hasil ekstraksi AI dari persetujuan bisnis.
Intake. Extraction. Validation. Decision. Persistence. Audit.

Nilai proyek ini berada pada arsitektur proses yang dapat diperiksa. Tidak ada klaim persentase akurasi atau penghematan waktu sebelum pengujian dengan data dan kriteria evaluasi yang sesuai.
